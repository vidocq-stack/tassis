= Tassis
:description: Jakarta Messaging 3.1 provider with its own in-VM broker: zero third-party dependency, strict Java Modules, virtual threads.

image::tassis-logo.png[Tassis,300,role=module-logo]

[.lead]
Tassis is a Jakarta Messaging 3.1 provider written in Java 25. It depends on the Jakarta Messaging API and on nothing else, every artifact is a Java module, and the threads it creates are virtual threads. Being a provider, it ships its own broker, which today runs inside the JVM of the application that uses it.

[IMPORTANT]
====
Tassis is **in development and not released**: no artifact has been published. The classic API, the simplified API and the legacy domain-specific API work on the in-VM broker. Messages live in memory, and the network transport has no encryption yet. The limits a user must know are listed in the xref:reference.adoc#limits[reference]. This documentation describes the `{project-version}` development line.
====

== Origin of the name

The Tassis family, later Thurn und Taxis, ran the relay postal service that carried messages across Europe from the end of the 15th century. In 1490 Maximilian I of Habsburg entrusted Francesco de Tassis with a line of mounted couriers between Innsbruck and the Low Countries. A contract of 1505 with Philip the Handsome turned it into a network, with fixed routes and delivery times written into the contract. The family ran that post until 1867.

A sender hands a message to the network, and the network takes charge of delivering it to its destination. That is what a Jakarta Messaging provider does for Java applications: a producer sends a message to a queue or publishes it to a topic, and the provider delivers it to the consumers.

[cols="1,1",options="header"]
|===
| The Tassis post | Jakarta Messaging

| The sender hands a letter over and goes back to work, without waiting for the addressee.
| A producer sends a message and carries on. The consumer may be busy, or absent.

| The letter goes from relay to relay, and each relay keeps it until a fresh rider takes it over.
| The broker stores the message until a consumer takes it.

| A slip travels with the bag, and each relay writes on it the hour the bag went through.
| A message carries its headers: when it was sent, when it expires, whether it is being delivered again.

| The post horn announces the courier.
| A message listener is called when a message arrives.
|===

The post horn of the logo is the emblem of that post, and the dotted circle around it is the road and its relays. The spelling is the one the family used in the Low Countries and in Spain, _de Tassis_.

== At a glance

[cols="1,3"]
|===
| Implemented spec | https://jakarta.ee/specifications/messaging/3.1/jakarta-messaging-spec-3.1.html[Jakarta Messaging 3.1]
| Java | 25
| Java modules | `io.vidocq.tassis.api`, `io.vidocq.tassis.core`, `io.vidocq.tassis.cdi.vauban` for the injection of `JMSContext`, and `io.vidocq.tassis.server` to open a broker to the network.
| Runtime dependencies | None beyond the `jakarta.messaging` API module
| Broker | In the JVM of the application, entirely in memory: nothing is written to the file system, by design. It can be opened to the network with AMQP 1.0.
| Status | In development, not released
| Jakarta Messaging TCK | The 903 applicable functional tests pass, and the signature test passes. Compatibility is **not claimed**: see xref:tck.adoc[TCK status].
|===

== Three identifying traits

. **Zero third-party dependency.** `tassis-core` compiles against `jakarta.jms-api` and nothing else: no CDI, no JNDI, no library. The message selector parser is written by hand.
. **A broker of its own.** Tassis is not a client for another product's broker. Queues, topics, subscriptions, acknowledgement, local transactions and redelivery are implemented in `tassis-core`.
. **Strict Java Modules and virtual threads.** `io.vidocq.tassis.core` exports one package, which holds the three classes an application names. Message listeners and completion listeners run on virtual threads.

== Position in the ecosystem

`tassis-core` depends on no other Vidocq brick. One integration exists, in a module of its own: the xref:usage.adoc#injection[injection of `JMSContext`] with CDI through Vauban. Another is planned: XA with JTA enlistment through `mansart-transactions` (milestone M13). A `vidocq` runtime extension and CDI message listeners are out of the scope of the roadmap.
