== Which TCK

The Jakarta Messaging 3.1 TCK is published in two shapes. Tassis uses the Maven artifact `jakarta.tck:jms-tck:11.0.3`: JUnit 5 tests, named "Jakarta Messaging Outside container", compiled against `jakarta.jms-api:3.1.0`. The other shape, the JavaTest distribution `jakarta-messaging-tck-3.1.0.zip`, is only used for the signature file it contains.

The tests obtain their connection factories, queues and topics through a porting interface of the TCK, `TSJMSObjectsInterface`. The Tassis implementation is `io.vidocq.tassis.tck.TassisJmsObjects`: it returns `new TassisConnectionFactory()`, `new TassisQueue(name)` and `new TassisTopic(name)`. No JNDI is involved. For the factory the TCK uses for its topic tests, it returns `new TassisConnectionFactory().withClientID("cts")`.

== How to run it

From the root of the repository:

[source,bash]
----
# the tests Tassis is expected to pass today
./run-official-tck-messaging-3.1.sh

# another selection
./run-official-tck-messaging-3.1.sh -Dtck.test='**/core/selectorQueue/*IT'

# the signature test (downloads the JavaTest distribution of the TCK, 14 MB)
./run-official-tck-messaging-3.1.sh signature

# the same tests through the network
./run-official-tck-messaging-3.1.sh network
----

The script installs `tassis-api`, `tassis-core`, `tassis-amqp` and `tassis-server` locally, runs `./mvnw -Ptck -pl tassis-tck test`, and writes the counts and the verdict to `tassis-tck/target/tck-report.txt`.

The runner is the module `tassis-tck`. It joins the reactor only under the `tck` Maven profile, so a plain `./mvnw install` neither builds it nor downloads the TCK. It runs on the class path, in test scope only.

The selection run by default is the property `tck.test` of `tassis-tck/pom.xml`: the packages of `core` and `core20`, then the tests excluded by name, grouped by the milestone that will enable them.

The tests read `jms_timeout`, how long they wait for a message, from a system property. `tassis-tck` sets it to 3000 ms; the default of the TCK is 10000.

A full run reports 904 tests, because it also executes `PortingSmokeTest`, a test of the wiring itself. It takes about 13 minutes: many `core20` tests wait on purpose.

== Authentication

Two tests of `core20/connectionfactorytests/ClientIT`, `createConnectionExceptionTests` and `createJMSContextExceptionTests`, expect the credentials `("invalid", "invalid")` to be refused with a `JMSSecurityException`, while most of the suite connects without credentials and some of it with the user of its configuration. The porting class therefore secures the broker the way the suite expects a provider to be set up: it declares that user and allows anonymous connections. These two tests were excluded from the run until milestone M11.1.

== Signature test

The signature test checks that the API exposed by `tassis-api` is exactly the `jakarta.jms` API of the specification, with no member missing and none added. It runs `jakarta.tck:sigtest-maven-plugin` 2.7 in static mode on the classes of `jakarta.jms-api:3.1.0`, against the TCK's `jakarta.jms.sig`.

* The signature file is only published in the JavaTest distribution of the TCK, under the Eclipse Foundation TCK License. It is not kept in the repository: the script downloads the distribution into `tassis-tck/target/tck-distribution` and extracts the file.
* One class is ignored, `java.lang.Object`. The signature file was recorded on a JDK where `Object.finalize()` was not yet deprecated for removal, a difference every class inherits. Without that option the test reports 52 "added annotations", all of them this one; with it, none.
* Control: run against `jakarta.jms-api:3.0.0`, the test fails, on what 3.1 added.

`tassis-api` adds nothing to the upstream artifact, so the test passes by construction. It is run because a compatible implementation has to pass it, and it would catch a fork of the API.

[#deviations]
== Deviations from the TCK as published

Each of the following differs from running the TCK exactly as published. None skips or alters a test.

=== `jakarta.tck:common` pinned to 11.0.8

`jms-tck:11.0.3` declares `jakarta.tck:common:11.0.0-RC4`. In that release the TCK's own class `BytesMessageTestImpl` never assigns one of its fields, so two tests on foreign messages (`ForeignMsgQueueTestsIT#sendReceiveBytesMsgQueueTest` and its topic twin) fail with a `NullPointerException` before the provider is involved, with any provider. `common` 11.0.8 fixes it, and `tassis-tck` pins that version. To be revisited when a `jms-tck` release declares a fixed `common`.

=== Test methods run in alphabetical order

Some TCK classes only pass for some orders of their tests. In `TxTopicTestsIT`, one test creates a durable subscription and never unsubscribes; two other tests of the class reuse its name and assert on the first message they receive. With the default order of JUnit 5 they receive a message left by a test that ran in between, which any correct provider must deliver, and fail. `tassis-tck` sets `junit.jupiter.testmethod.order.default` to `MethodOrderer$MethodName`.

=== A timeout on every test

`tassis-tck` sets `junit.jupiter.execution.timeout.default` to 2 minutes. Several TCK tests wait on a latch that only a message listener releases; when the provider gets it wrong they wait for ever and hang the run. The timeout turns that into a failure.

=== Harness dependencies excluded

`jakarta.tck:common` brings Derby, Ant and `commons-httpclient` 3.1, which the standalone Messaging tests never load. `tassis-tck` excludes them, and the selection passes without them.

=== In-reactor runner

The older bricks of the Vidocq workspace keep their TCK runner out of their reactor. `tassis-tck` is in the reactor, behind the `tck` profile.

None filed.

[#network]
== Through the network

The TCK knows nothing of a transport: it asks the porting class for connection factories. With `network`, `TassisJmsObjects` starts a `TassisServer` on a free port in front of the default broker and returns factories whose URL is `tassis:amqp://localhost:<port>`. Every connection of every test then goes through the AMQP client of `tassis-amqp`, a socket, and the server of `tassis-server`, to the broker the direct run uses.

Same selection, same settings, same result: 903 passed, 0 failed, in about 14 minutes. Nothing is excluded and nothing is adapted for that run. It is the proof asked of the client transport (milestone M11.3d), and it tests the server as much as the client.

The direct run stays the reference: it is the one that says what the provider does. The run through the network is to be replayed when the client transport, the server or the interface between client and broker changes.

That run uses consumers as they come, which ask for one message at a time. With consumers told to xref:usage.adoc#prefetch[fetch ahead] (`-Dtassis.tck.prefetch=100`), 899 tests pass and 4 fail: the shared-consumer tests of `core20`, where a first consumer receives a message and a second is expected to get the next, which the first already holds. That is the price of the setting, and why it is not the default.
