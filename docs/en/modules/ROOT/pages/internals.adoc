= Internals
:description: For contributors: the modules and packages of Tassis, storages and subscriptions, deliveries, the selector index, the threads Tassis creates, the lock order, and close() versus shut().

[.lead]
For contributors: where the code lives and the rules it obeys. Users do not need this page. The public surface is the Jakarta Messaging API plus the three classes of the package `io.vidocq.tassis.core`.

Group id `io.vidocq.tassis`, parent `io.vidocq:vidocq-parent`.

== Packages of `tassis-core`

`io.vidocq.tassis.core` is the only exported package. It holds `TassisConnectionFactory`, `TassisQueue` and `TassisTopic`, what a client must name, and `TassisBroker`, the administration of a broker. Everything else is under `io.vidocq.tassis.core.internal` and is not exported.

[cols="1,3",options="header"]
|===
| Package | Content

| `internal.message`
| `TassisMessage` (header fields, properties, the template for a body) and one subclass per body type: text, object, map, bytes, stream. `ValueConversions` is the single conversion table for properties, `MapMessage` and `StreamMessage`. `Messages.snapshot` turns any `Message`, including another provider's, into an independent Tassis copy.

| `internal.broker`
| `BrokerConnection`: the interface through which a client connection reaches its broker, and the only thing the client objects know of it. `Broker`: the registry of brokers by name, queues, subscriptions, client identifiers, temporary destinations, and the delivery of messages. `LocalConnection`: what a `Broker` keeps for one client, and the implementation of `BrokerConnection` for the broker of the JVM. `Users`: the user registry of a broker and the check of the credentials a connection is created with. It guards itself and is never touched under the broker lock; a password is kept as a salted SHA-256 digest and compared in constant time.

| `internal.client`
| The API objects: `TassisConnection`, `TassisSession`, `TassisMessageProducer`, `TassisMessageConsumer`, `TassisQueueBrowser`, the temporary destinations, and the simplified API (`TassisContext`, `TassisJMSProducer`, `TassisJMSConsumer`). `Destinations.resolve` is the one place that decides which `Destination` objects belong to Tassis.

| `internal.selector`
| `Selector` (a compiled selector), `SelectorParser` (a hand-written lexer and recursive-descent parser, with the grammar as a comment) and `Expression` (the tree and its evaluation, where `null` stands for SQL's unknown).

| `internal.settings`
| `Settings`, one record: what configures a connection factory, read from keys or from a connection URL, with the defaults and the validation. A new setting is added there once, as a key and as a URL parameter.
|===

There is no storage interface: messages live in the memory of the broker, in `Broker.Storage`, and the broker is in memory by decision.

== The seam between client and broker

The client objects never name the class `Broker`. `TassisConnectionFactory` obtains a `BrokerConnection` from `Broker.connect(userName, password)`, which is also where the credentials are checked, and every client object goes through it: `TassisConnection.link()`, `TassisSession.link()`. It has two implementations: `LocalConnection`, for the broker of the JVM, and `AmqpBrokerConnection`, in `tassis-amqp`, for a broker of the network (see <<client>>). `Transports.connect` chooses from the settings of the factory. It is written for a broker that may be far away and whose client may vanish:

* **The broker reads nothing from the client.** It is told what it needs to know: `start()` and `stop()` for the connection, `listen(boolean)` for a consumer that gains or loses its listener. No client code runs under the broker lock.
* **The broker keeps every delivery that is not settled**, in `LocalConnection.unsettled`, until the client settles it or gives it back.
* **The broker knows who the connection is.** Nothing in a request names its sender: the client identifier, or else the connection itself, is what `noLocal` compares.
* **`close()` takes back what is left**: it closes the remaining consumers, gives back the unsettled deliveries, deletes the temporary destinations of the connection and frees its client identifier. A client that closes in good order leaves it little to do; a lost connection will arrive there with everything.

The interface stays at the level of the connection. There is no session on the broker's side: a transacted session buffers its sends and hands them over, with the deliveries to settle, in one `commit` request.

== Storage and subscriptions

`Broker.Storage` holds the messages waiting for the consumers of **one queue or one subscription**, in a `TreeSet` ordered by priority, highest first, then by a sequence number the broker assigns when it stores the message.

* A queue has one storage, created on first use.
* A subscription (`Broker.Subscription`) is a subscription request plus a storage of its own.
* `Broker.commit`, which a send outside a transaction also goes through, adds a message sent to a queue to the storage of that queue. It adds a message published to a topic to the storage of each subscription of that topic, after applying the subscription's selector and its `noLocal` rule. The same message object is shared by all those storages; it is never modified.

From there on a subscription behaves like a queue, so receive, acknowledgement, transactions and redelivery are one code path for both.

Named subscriptions are indexed by a key made of three values: durable or not, the client identifier, the name. The creation, reuse, replacement and conflict rules of section 8.3 of the specification are in one private method of `Broker`, `named(LocalConnection, Subscribing)`.

A send never hands the broker the client's own message: `TassisMessageProducer` passes `Messages.snapshot(message)`.

== Delivery

A receive takes the first deliverable message of the storage a consumer is attached to, removes it from the storage and returns a `Delivery`: the stored entry, plus a copy of the message made for this delivery, marked with its delivery count. Unless the caller asked for it to be settled on delivery, the broker also records it among the unsettled deliveries of the connection.

From that moment **the consumer's session answers for the delivery**. It does one of three things with it, each a request to the broker:

* `settle`, alone or as part of a `commit`: the broker forgets the delivery, and the message is consumed for good;
* `redeliver`: the entry returns to its storage with its sequence number, hence to its place, and its next delivery is a redelivery;
* `returnUndelivered`, when the application never saw the message: the delivery count is decremented, as if the message had not been taken.

Each of the three does nothing for a delivery that is no longer the connection's, so a delivery cannot be given back twice: not by a session and by the closing of its connection, for instance. `TassisSession` keeps the deliveries it answers for in its `unsettled` list. A `receive` of an automatically acknowledged session asks for settlement on delivery and keeps nothing; a listener of such a session is settled when `onMessage` returns.

`Storage.add` and `Storage.remove` are the only two ways to change what a storage holds: they keep the selector index and the next expiration time up to date.

== The per-selector index

A consumer on a queue with a selector must not scan, on each receive, the messages its selector rejects. Each selector in use on a queue therefore has a `Broker.View`: the ordered set of the messages of the queue that the selector accepts.

* The view is built by one scan of the queue when the first consumer with that selector attaches, and removed when the last one detaches.
* `Storage.add` adds a new message to each view whose selector accepts it, and `Storage.remove` removes it from all of them.
* What a selector answered for a message is remembered on the stored entry, so a message is evaluated once per selector, whatever the number of consumers and of receives.
* A receive through a view takes the head of the view.

Two cases stay outside the index:

* a selector that refers to `JMSXDeliveryCount` gets no view, because its answer changes from one delivery to the next. Its consumers scan the queue and evaluate the selector on each receive;
* a subscription needs no view: its selector is applied when the message is published. If that selector refers to the delivery count, it is checked again when a message that was given back is about to be redelivered, and a message that no longer matches leaves the subscription.

Selectors are evaluated under the broker lock.

Expired messages are removed by `Storage.sweepExpired`, which a receive calls on the whole storage, not on the view: a consumer that reads through a view would otherwise never meet the expired messages its selector rejects. The sweep only happens when a consumer of a started connection receives.

== Threads

Tassis creates two kinds of thread, both virtual.

=== The dispatcher of a consumer

`setMessageListener` with a non-null listener starts a virtual thread for the consumer, running `TassisMessageConsumer.dispatch`. The dispatcher loops:

. it takes one message with `Consumer.take(period)`, which waits for as long as the consumer listens without interruption. `listen(boolean)` returns the number of the period it opens or continues, and that number changes each time the consumer stops listening: a dispatcher that served a listener since removed is thus never mistaken for the dispatcher of the next one. A `take` that returns nothing ends the dispatcher;
. it hands the delivery to `TassisSession.dispatch`, which takes the session's `listeners` lock, waits while the connection is stopped, calls `onMessage`, then settles the message or handles the failure.

All the `onMessage` calls of a session go through `TassisSession.dispatch`. That lock is what makes the listeners of a session serial.

If the consumer is closed or loses its listener while the dispatcher holds a message, the message goes back with `returnUndelivered`.

=== The completion thread of a session

The first asynchronous send of a session creates a single-thread executor on a virtual thread. `TassisSession.completed` queues the notification of each send on it, so the `onCompletion` callbacks of a session run one at a time, in send order. The send itself has already been made, in the caller's thread.

The session counts the pending callbacks. `close`, `commit`, `rollback` and the `close` of a producer wait for that count to reach zero.

=== Recognising a callback

A session records which thread is currently inside one of its message listeners and which is inside one of its completion listeners. That is how the calls a callback may not make are refused (see xref:usage.adoc#listeners[Usage]), and how a session that is being closed stays usable by the listener the close is waiting for.

== Locks and their order

[cols="1,3",options="header"]
|===
| Lock | Guards

| `TassisSession.listeners`
| Held around every `onMessage` call of the session.

| `TassisSession.work`
| The session's unsettled deliveries, its uncommitted sends, and the bookkeeping of its completion callbacks.

| The broker lock (`Broker.lock`)
| All broker state, that of its connections included: whether a connection is started, its consumers and whether each one listens, its unsettled deliveries, its temporary destinations.
|===

The only order in which they are taken is: **`listeners`, then `work`, then the broker lock**. Nothing that runs under the broker lock may take a session lock or call application code.

Whatever delivery depends on is state of the broker, changed by a `BrokerConnection` request that signals the condition every waiting receive listens to. The client keeps no such state of its own: a consumer's `listener` and `dispatcher` fields only say what the client does with a message once it has it.

Two other locks exist beside these three: `TassisContext.lifecycle`, which guards the lazily created session of a context and is never held while waiting for a callback to return, and `TassisConnection.identity`, which serialises the calls to `setClientID`.

One broker lock is the simplest design that honours `stop()` and `close()`. Its known costs: every state change wakes every waiting receive of the broker, and a receive without a view scans past the messages that are delayed. Whether the lock must be split is left to the benchmarks of milestone M12.

== `close()` versus `shut()`

Closing has two entry points.

* `close()` is the public method of the API. It applies the restrictions on callbacks: a session refuses to be closed by one of its own listeners, a producer waits for the completion callbacks.
* `shut()` is what a parent uses to close a child: a connection shuts its sessions, a session shuts its producers, consumers and browsers (the `SessionChild` interface). It applies no restriction on the calling thread, never throws, may be called more than once, and returns only once the child is quiet.

Creation and close can race. A session adds a new child to its list **first**, then checks whether it is closed, and shuts the child if so. A concurrent close therefore either sees the child in the list or has already raised the flag the creation checks. `TassisConnection` does the same for its sessions and its temporary destinations. `CloseRaceTest` is the regression test.

== The simplified API

`TassisContext`, `TassisJMSProducer` and `TassisJMSConsumer` hold no messaging behaviour. They delegate to the classic objects through `Unchecked`, which turns each checked `JMSException` into its unchecked counterpart. New behaviour goes in the classic classes.

A context creates its session on first need, not in its constructor, so that `setClientID` still works on a new context. The contexts created from one another share a connection and a counter of open contexts; the connection is closed when the counter reaches zero.

[#injection]
== Injection of `JMSContext`

`tassis-cdi-vauban` holds four classes in a package that is not exported, and `TassisCdi`, which names the two beans for a container built by hand.

* `JmsContextProducer` produces what `@Inject JMSContext` receives. The three Messaging annotations are not CDI qualifiers, so one producer serves every injection point and reads them from its `InjectionPoint` into a `ContextKey`.
* What it produces is an `InjectedJMSContext`: a facade with no state of its own, which refuses the methods of §12.4.5 and delegates the others to the context that `RequestContexts` gives for its key **at each call**.
* `RequestContexts` is request scoped. The facade holds its client proxy, so the same injected object reaches the contexts of whichever request is in progress. It creates a context on first use, under a lock, as the subtasks of a request share its scope; it closes them all in its `@PreDestroy`, logging a close that fails so that the others are still closed.

Nothing is reflective. Vauban's annotation processor generates, in the package of the beans, a `VaubanComponentProvider` that instantiates and injects them from inside the module, and the module descriptor declares it. That is why the package is neither exported nor opened. CDI and Vauban are `requires static`: the application that injects has them on its module path through Vauban, and the module asks nothing of an application that does not.

`tassis-cdi-vauban-module-it` proves it: an application module, its bean processed at build time, runs on the module path with no `--add-opens` and checks that the annotations of its injection points reached the producer.

[#amqp]
== The AMQP 1.0 codec

`tassis-amqp` (Java module `io.vidocq.tassis.amqp`) reads and writes what AMQP 1.0 puts on the wire. It holds no connection, session or link: those are the server's. It exports its packages to `tassis-server` only, and depends on `tassis-core` for one package, `internal.jms`.

[cols="1,3",options="header"]
|===
| Package | Content

| `internal.types`
| The values of AMQP (part 1 of the specification) and their encodings. Java types where they are exact, and one small type for each AMQP type Java lacks: `UByte`, `UShort`, `UInt`, `ULong`, `Symbol`, `Binary`, `Timestamp`, `AmqpChar`, the decimals, `AmqpArray`, `Described`. `AmqpEncoder` writes the shortest encoding a value allows; `AmqpDecoder` reads them all.

| `internal.transport`
| The protocol headers, the frame and `FrameCodec`, the nine performatives, `AmqpError` (part 2).

| `internal.messaging`
| The sections of a message and `AmqpMessage`, sources and targets, delivery states (part 3).

| `internal.transactions`
| The coordinator, `declare`, `discharge`, and the transactional state (part 4).

| `internal.security`
| The five bodies of a SASL frame (part 5).

| `internal.jms`
| `JmsMessageCodec`: a `TassisMessage` as an `AmqpMessage`, and back. AMQP defines no such mapping; the conventions are those of Apache Qpid JMS: an annotation for the type of message, two for the kind of destination, the header fields of JMS spread over the header and the properties sections. An object message travels as its serialized form and is never deserialized on the way.
|===

`AmqpTypes.ALL` is the registry of the 40 described types Tassis knows, by numeric and by symbolic descriptor. A described value whose descriptor it does not know stays a `Described`, as the specification asks.

Each composite type is a record whose fields are those of the specification, in its order. A field the peer left out is `null`: the defaults the specification gives are applied by whoever reads the field, not by the codec, so that a value read and written back is unchanged. There is no reflection: each record lists its fields and rebuilds itself from them.

The decoder reads octets that come from a peer and trusts them for nothing. A size is checked against what is left to read before anything is allocated for it, a count against the octets that could hold it, nesting is bounded (`AmqpDecoder.MAX_DEPTH`), and whatever is wrong is an `AmqpDecodeException`. `HostileInputTest` holds the cases, among them hundreds of thousands of random and mutated inputs.

The proof that these octets are AMQP 1.0, and not a private reading of it, is in `tassis-interop`:

* every primitive value and every described type is written by Tassis and read by Apache Qpid Proton-J, and the reverse; for the primitive values the octets are compared too;
* for each composite type, the accessors of Proton-J, named after the fields of the specification, must return what Tassis wrote at each position: this is what catches two fields in the wrong order;
* an embedded Apache ActiveMQ Artemis is spoken to frame by frame: SASL, `open`, a session, a link, a message sent to a queue and received back.

[source,bash]
----
./mvnw -Pinterop -pl tassis-interop -am verify
----

[#server]
== The AMQP server

`tassis-server` puts a listener in front of a broker. It is a client of `BrokerConnection`, the seam of milestone M11.2, exactly as the client objects of `tassis-core` are. Serving the whole of Jakarta Messaging asked two things of that interface: a way to find a durable subscription by its name, and subscription names that are the broker's rather than a client identifier's, since every AMQP connection has a container identifier whether its client set one or not.

Each connection, an `AmqpConnection`, is served by virtual threads of three kinds:

* the **reader** reads the frames and does what each asks. It never writes to the socket, so a client that does not read cannot hold it up;
* the **writer** writes the frames the others queue, in the order they were queued, and an empty frame when it has had nothing to write for half the time-out the client announced;
* one **pump** per link the client receives by (`OutgoingLink`) takes messages from the broker and queues their transfers, for as long as the client has credit.

One lock per connection guards its sessions, its links, their credit and the deliveries sent and not settled. It is taken before the broker's lock, never after, and is not held while waiting for the broker or for the socket.

How AMQP meets the seam:

[cols="1,1",options="header"]
|===
| AMQP | `BrokerConnection`

| SASL `PLAIN` or `ANONYMOUS` | `Broker.connect(user, password)`
| `open` asking for `sole-connection-for-container` | `claimClientId(container-id)`
| A transfer on a link the client sends by | `send`, then a disposition `accepted`
| `attach` of a link the client receives by | `attach(queue, selector)`, or `subscribe` for a topic: the name of the link is the name of the subscription, the source says whether it is durable and shared
| `attach` with the distribution mode `copy` | `browse`: a snapshot, sent as credit comes and settled as it goes
| `attach` of a sending link whose target is dynamic | `createTemporaryQueue` or `createTemporaryTopic`; closing the link deletes it
| `attach` of a receiving link without a source, then its closing | `durableSubscriptionTopic`, then `unsubscribe`
| A link to the coordinator: `declare`, transfers and dispositions that name the transaction, `discharge` | Sends and acknowledgements are kept in a `Transaction`, then `commit(sends, consumed)`, or `redeliver(consumed)` to roll back
| Credit granted with `flow` | `Consumer.listen(true)` and `take(period)` by the pump
| Credit taken back, or `drain` | `Consumer.listen(false)`, which ends the pump's wait
| Disposition `accepted`, or `rejected` | `settle`
| Disposition `released` | `returnUndelivered`
| Disposition `modified` | `redeliver`, or `settle` if the client will never take the message
| `detach`, `end` | `Consumer.close()`, and `redeliver` of what the link had not settled
| `close`, or the socket lost | `close()`, which takes back whatever is left
|===

The listening period of `Consumer.listen`, made for message listeners, is what delivery by credit needed: the reader changes the state of the link, then ends the period, and the pump either sees the state or has its wait ended.

A link the server cannot attach (an invalid selector, a temporary destination that is gone, a subscription in use) is refused the way AMQP prescribes: attached with nothing at the server's end, then detached with the reason, which leaves the session usable. What a peer does out of place ends the connection with the matching error. `Limits` holds what the server announces and accepts.

`TassisServerTest` drives the server frame by frame with the codec. `QpidJmsAgainstTassisTest`, in `tassis-interop`, runs Apache Qpid JMS against it.

[#client]
== The AMQP client

`tassis-core` does not depend on `tassis-amqp`. It declares that it `uses` the service `Transport`, an interface of `internal.broker`, and `tassis-amqp` `provides` it with `AmqpTransport`; a file under `META-INF/services` says the same for a class path. `Transports.connect` asks the `ServiceLoader` for the transport a URL names.

An `AmqpBrokerConnection` is one socket, one AMQP connection and one session. Two virtual threads serve it, as on the server: a reader that records what the broker says and never writes, and a writer that alone writes, and sends an empty frame when it has had nothing to say for half the time-out the broker announced. One lock guards everything and one condition wakes whoever waits; every wait releases the lock, and frames are queued under it, so that the order of the wire is the order of the decisions.

How the seam meets AMQP, from the client's side:

[cols="1,1",options="header"]
|===
| `BrokerConnection` | AMQP

| `Transport.connect(settings, user, password)` | The socket, SASL `PLAIN` or `ANONYMOUS`, `open`, `begin`, and a sending link without an address
| `claimClientId` | Another connection, opened with that container identifier and `sole-connection-for-container`: AMQP says who a connection is when it opens. A connection without a client identifier asks for no such thing, so that its subscription names are the broker's
| `send` | A transfer on the link without an address (an anonymous relay), then the wait for its disposition
| `commit(sends, consumed)` | `declare`, the transfers and the dispositions in the transaction, `discharge`. A commit that only acknowledges, or sends one message, needs no transaction
| `attach`, `subscribe` | A receiving link, described as the server reads it
| `receive`, `take` | One credit, then the wait. Out of time, or the listener gone: a `flow` with `drain`, so that the broker sends what it has or says it has nothing
| `stop` | `drain` on every link, and `released` for what came and nobody had seen
| `settle`, `redeliver`, `returnUndelivered` | Dispositions `accepted`, `modified` with `delivery-failed`, `released`
| `Consumer.close()` | `drain`, then `detach`: put off while the session still answers for deliveries of the link, which a broker gives back when a link goes
| `browse` | A link in the mode `copy`, credit and `drain` together until the broker has nothing more
| `createTemporaryQueue`, `deleteTemporaryQueue` | A sending link with a dynamic target, kept until the destination is deleted
| `unsubscribe` | A receiving link without a source, closed
| `onLost` | The reader ended and nobody had closed: every wait ends, and the listener is called on a thread of its own
|===

Two exchanges have no answer of their own in AMQP, and the client needs one. To know the broker has given back what it was told to (`redeliver`, `returnUndelivered`), it sends a session `flow` that asks for an echo: the server answers in the order it reads. And a `drain` is over when the credit is used, by a transfer, or given up, by a `flow` whose delivery count accounts for all of it; an answer that does not is that of an earlier drain.

`NetworkClientTest`, in `tassis-server`, runs the Jakarta Messaging API through a real socket; the TCK run with `network` does the same with the whole suite.

== House rules

The rules of the repository's `CLAUDE.md` apply. The ones that shape the code described here:

* `tassis-core` depends on nothing beyond `jakarta.jms-api`;
* an API method that is not implemented throws `UnsupportedOperationException` with a pointer to the roadmap, never a stub that returns wrong data;
* no `synchronized` around a blocking call, no `ThreadLocal`;
* tests come first, cite the section of the specification they cover, and use JUnit with hand-written fixtures;
* say **Java Modules**, never the abbreviation.
