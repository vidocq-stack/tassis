= Usage
:description: Queues, topics and subscriptions, acknowledgement and transactions, redelivery, selectors, listeners, asynchronous send, temporary destinations, browsers and the simplified API with Tassis.

[.lead]
Everything on this page is the standard Jakarta Messaging 3.1 API. The only Tassis classes an application names are `TassisConnectionFactory`, `TassisQueue` and `TassisTopic`. Where the specification leaves a choice to the provider, this page says which one Tassis made.

Unless stated otherwise the snippets use the classic API and assume a started `connection`, a `session` created by `connection.createSession()`, and that the enclosing method declares `throws JMSException`.

== Queues

A message sent to a queue waits there until one consumer takes it. If the queue has several consumers, each message goes to one of them only.

[source,java]
----
Queue queue = session.createQueue("orders");
MessageProducer producer = session.createProducer(queue);
MessageConsumer consumer = session.createConsumer(queue);

producer.send(session.createTextMessage("low"), DeliveryMode.PERSISTENT, 1, 0);
producer.send(session.createTextMessage("high"), DeliveryMode.PERSISTENT, 9, 0);

((TextMessage) consumer.receive(5_000)).getText();   // high
((TextMessage) consumer.receive(5_000)).getText();   // low
----

* Messages are delivered by priority, highest first, then in the order they were sent.
* A message with a time to live is not delivered after it has expired. A message with a delivery delay is not delivered before its delivery time.
* `receive()` and `receive(0)` wait without limit, `receive(timeout)` waits that many milliseconds, `receiveNoWait()` does not wait. The last two return `null` when no message came in time, and a blocked `receive` returns `null` when its consumer is closed.
* While the connection is stopped, nothing is delivered, but the timeout of a `receive` keeps running.
* A producer created with `session.createProducer(null)` has no destination: each `send` names one. Naming a destination on a producer that already has one, or omitting it on a producer that has none, throws `UnsupportedOperationException`.
* A send stores a copy of the message. Changing the message after the send has no effect on what is delivered, and the message a consumer receives is read-only.
* `setDisableMessageID` and `setDisableMessageTimestamp` are recorded and ignored: every message gets an identifier and a timestamp.
* `DeliveryMode.PERSISTENT` is accepted, and is the default, but no message survives the JVM: the broker is in memory by design. See xref:reference.adoc#limits[Limits].

The legacy queue API (`QueueConnection`, `QueueSession`, `QueueSender`, `QueueReceiver`) is available through `createQueueConnection()`.

== Topics and subscriptions

A message published to a topic is copied into each subscription the topic has at that moment. A topic without a subscription drops what is published to it.

[source,java]
----
Topic topic = session.createTopic("news");
MessageConsumer first = session.createConsumer(topic);
MessageConsumer second = session.createConsumer(topic);

session.createProducer(topic).send(session.createTextMessage("headline"));

((TextMessage) first.receive(5_000)).getText();    // headline
((TextMessage) second.receive(5_000)).getText();   // headline
----

=== The four kinds of subscription

[cols="2,3,2,3",options="header"]
|===
| Kind | Created by | Consumers | Ends

| Unshared, non-durable
| `createConsumer(topic)`
| One: the consumer that created it
| When that consumer is closed

| Shared, non-durable
| `createSharedConsumer(topic, name)`
| Several, which share the messages
| When its last consumer is closed

| Unshared, durable
| `createDurableConsumer(topic, name)`
| One at a time
| On `unsubscribe(name)`

| Shared, durable
| `createSharedDurableConsumer(topic, name)`
| Several, which share the messages
| On `unsubscribe(name)`
|===

The four methods exist on `Session` and on `JMSContext`, each with a variant that takes a message selector. `createDurableSubscriber` of the classic API creates an unshared durable subscription too.

A durable subscription keeps receiving what is published while it has no consumer, and survives the connection that created it:

[source,java]
----
Connection reader = factory.withClientID("reader").createConnection();
reader.start();
Session readerSession = reader.createSession();

readerSession.createDurableConsumer(topic, "inbox").close();

session.createProducer(topic).send(session.createTextMessage("while away"));

MessageConsumer inbox = readerSession.createDurableConsumer(topic, "inbox");
((TextMessage) inbox.receive(5_000)).getText();   // while away
----

Rules that apply to named subscriptions:

* An **unshared durable** subscription needs a client identifier on its connection: without one, creating it throws `IllegalStateException`. A second consumer on it while the first is open throws `JMSException`.
* A **shared** subscription, durable or not, needs no client identifier.
* A subscription name is scoped by the client identifier of the connection. The same name used with two different client identifiers, or with and without one, designates two subscriptions.
* Creating a consumer on an existing name with the same topic, the same selector and the same `noLocal` value reuses the subscription. Two selectors are the same when their texts are equal.
* Creating a consumer on an existing name with another topic or another selector deletes the subscription, with its messages, and starts a new one. If the subscription has an open consumer at that moment, the call throws `JMSException` instead.
* Shared and unshared durable subscriptions share one namespace: a name used by one kind cannot be used by the other, and the attempt throws `JMSException`. Shared non-durable subscriptions have a namespace of their own.
* `unsubscribe(name)` deletes a durable subscription. It throws `JMSException` while the subscription has an open consumer, and `InvalidDestinationException` when no durable subscription has that name.

Durable subscriptions are kept in the memory of the broker: they survive connections, not the JVM. See xref:reference.adoc#limits[Limits].

=== Client identifiers

There are two ways to give a connection its client identifier.

`TassisConnectionFactory.withClientID` returns a factory whose connections are created with the identifier; the setting `tassis.clientId` does the same from outside the code (see xref:reference.adoc#configuration[Configuration]). The method is specific to Tassis, so `factory` must be declared as a `TassisConnectionFactory` to call it:

[source,java]
----
try (Connection configured = factory.withClientID("configured").createConnection()) {
    configured.getClientID();   // configured
}
----

Such a connection rejects `setClientID` with `IllegalStateException`, and only one of them can be open at a time: creating a second one throws `InvalidClientIDException`.

`Connection.setClientID` sets it on an existing connection, provided nothing else was done with the connection:

[source,java]
----
try (Connection fresh = factory.createConnection()) {
    fresh.setClientID("reader");
}
----

* `setClientID` throws `IllegalStateException` once the connection has been used: after `createSession`, `start`, `stop`, `getMetaData`, `getExceptionListener` or `setExceptionListener`. `getClientID` does not count as a use.
* It throws `IllegalStateException` if the identifier is already set, and `InvalidClientIDException` if the identifier is null, empty, or held by another open connection of the same broker.
* The identifier is released when the connection is closed.

On a `JMSContext`, `setClientID` works on a context newly created by the factory: the context creates its session on first need, and `createQueue`, `createTopic` and the methods that create messages do not need one.

=== `noLocal`

`createConsumer(topic, selector, true)` creates a subscription that ignores what its own connection publishes. When the connection has a client identifier, the comparison is made on the identifier, so a durable `noLocal` subscription keeps ignoring its owner after a reconnection. On a queue, `noLocal` is ignored.

The legacy topic API (`TopicConnection`, `TopicSession`, `TopicPublisher`, `TopicSubscriber`) is available through `createTopicConnection()`. A `QueueSession` rejects the topic methods it inherits, and a `TopicSession` the queue methods, with `IllegalStateException`.

== Acknowledgement modes and local transactions

[cols="2,5",options="header"]
|===
| Session mode | Behaviour

| `AUTO_ACKNOWLEDGE` (default)
| A message returned by `receive` is acknowledged at once. A message given to a listener is acknowledged when `onMessage` returns.

| `DUPS_OK_ACKNOWLEDGE`
| Exactly the same as `AUTO_ACKNOWLEDGE`: Tassis does not acknowledge lazily, so it delivers no duplicate.

| `CLIENT_ACKNOWLEDGE`
| `Message.acknowledge()` acknowledges every message the session has consumed so far, not only the one it is called on. `Session.recover()` gives the unacknowledged messages back for redelivery.

| `SESSION_TRANSACTED`
| Sends are held until `commit()`. `rollback()` discards them and gives the consumed messages back for redelivery.
|===

[source,java]
----
try (Session transacted = connection.createSession(Session.SESSION_TRANSACTED)) {
    transacted.createProducer(queue).send(transacted.createTextMessage("one"));
    // nothing is on the queue yet
    transacted.commit();
    // "one" is on the queue
}
----

* `createSession(true, anyMode)` creates a transacted session. `createSession(false, Session.SESSION_TRANSACTED)` and an unknown mode throw `JMSException`.
* `commit` and `rollback` on a session that is not transacted throw `IllegalStateException`, as does `recover` on a transacted session.
* A commit sends all the messages of the transaction or none. If one of them cannot be sent, because it names a temporary destination that was deleted since the send, the transaction is rolled back and `commit` throws `TransactionRolledBackException`.
* Closing a transacted session rolls its transaction back. Closing a client-acknowledged session acknowledges nothing: its unacknowledged messages are given back.
* `Message.acknowledge()` does nothing in the other modes, and throws `IllegalStateException` once its client-acknowledged session is closed.

These are local transactions: they cover one session. XA is planned for milestone M13.

== Redelivery

A message is redelivered when the session that consumed it gives it back: `rollback`, `recover`, the close of a session that has unsettled messages, or a listener that throws in an automatically acknowledged session.

[source,java]
----
try (Session transacted = connection.createSession(Session.SESSION_TRANSACTED)) {
    MessageConsumer consumer = transacted.createConsumer(queue);
    Message first = consumer.receive(5_000);
    first.getJMSRedelivered();                    // false
    first.getIntProperty("JMSXDeliveryCount");    // 1

    transacted.rollback();

    Message again = consumer.receive(5_000);
    again.getJMSRedelivered();                    // true
    again.getIntProperty("JMSXDeliveryCount");    // 2
    transacted.commit();
}
----

* `JMSXDeliveryCount` is set on every delivery, starting at 1. `JMSRedelivered` is true from the second delivery on.
* A message given back returns to the place it had in its queue or subscription, ahead of the messages sent after it.
* It is available again immediately: there is no redelivery delay.
* There is no redelivery limit for `receive`, for client-acknowledged listeners or for transacted sessions: a message that is always rolled back is redelivered for ever. The one limit that exists concerns automatically acknowledged listeners, and is described under <<listeners>>.

== Message selectors

A selector is given when a consumer or a browser is created. Tassis implements the syntax of section 3.8.1.1 of the specification.

[source,java]
----
MessageConsumer blue = session.createConsumer(queue, "color = 'blue'");

TextMessage red = session.createTextMessage("red one");
red.setStringProperty("color", "red");
session.createProducer(queue).send(red);

blue.receiveNoWait();   // null: the red message stays on the queue for another consumer
----

* **On a queue**, a message the selector rejects stays on the queue, available to the other consumers.
* **On a topic**, a message the selector rejects never enters the subscription.
* A null or blank selector means no selector, and `getMessageSelector()` then returns `null`.
* An invalid selector is rejected with `InvalidSelectorException` when the consumer or the browser is created.
* A selector can refer to six header fields: `JMSDeliveryMode`, `JMSPriority`, `JMSMessageID`, `JMSTimestamp`, `JMSCorrelationID` and `JMSType`. Any other name that starts with `JMS`, except the `JMSX` and `JMS_` properties, is rejected. `JMSDeliveryMode` is compared with the strings `'PERSISTENT'` and `'NON_PERSISTENT'`.
* Tassis checks types when the selector is given, where the literals make it possible: `weight > 'foo'` and `TRUE = 0` are invalid selectors. The type of a property is only known per message; a mismatch there makes the comparison false, or unknown inside an arithmetic expression.
* A property keeps its own type in a selector: no property conversion applies.
* `JMSXDeliveryCount` in a selector is the count of the delivery being considered: `JMSXDeliveryCount = 1` selects first deliveries only.

[#listeners]
== Message listeners

A consumer with a listener receives its messages asynchronously, on a virtual thread that Tassis creates for it.

[source,java]
----
MessageConsumer consumer = session.createConsumer(queue);
consumer.setMessageListener(message -> process(message));
----

* The listeners of one session are never called concurrently. Listeners of two different sessions can run at the same time.
* No listener is called while the connection is stopped. `Connection.stop()` returns only once the listener in progress has returned, and so does the `close()` of a consumer whose listener is running.
* A consumer that has a listener refuses `receive`, `receive(timeout)` and `receiveNoWait` with `IllegalStateException`. `setMessageListener(null)` stops the asynchronous delivery, after which the consumer can receive synchronously again.

What happens when `onMessage` throws depends on the session mode:

* **Automatically acknowledged session**: the message is redelivered at once, with `JMSRedelivered` set. If the listener still fails on a delivery whose `JMSXDeliveryCount` has reached 10, the message is **dropped** and an error is logged through `System.Logger`. There is no dead-letter queue. The number 10 is the default of the setting `tassis.listener.maxDeliveries`: see xref:reference.adoc#configuration[Configuration].
* **Client-acknowledged or transacted session**: the failure is logged and the session moves on to the next message. The message stays unacknowledged, or part of the transaction, and the application decides what to do with it.

An `Error` thrown by a listener is handled like a `RuntimeException`.

In an automatically acknowledged session, a listener that calls `session.recover()` gets the message it is processing redelivered, since that message is only acknowledged when `onMessage` returns.

=== What a callback may not do

From `onMessage`, these calls throw `IllegalStateException`:

* `Session.close()` on the session the listener belongs to;
* `Connection.stop()` and `Connection.close()` on the connection the listener belongs to.

Of the two behaviours the specification permits for these calls, failing or completing, Tassis chose the one that cannot deadlock.

A listener may close its own consumer, replace its own listener, and call `commit`, `rollback` and `recover` on its session.

== Asynchronous send

[source,java]
----
MessageProducer producer = session.createProducer(queue);
TextMessage message = session.createTextMessage("async");

producer.send(message, new CompletionListener() {
    @Override
    public void onCompletion(Message sent) {
        // called on another thread, once the message is sent
    }

    @Override
    public void onException(Message failed, Exception exception) {
    }
});
----

* With the in-VM broker a send is complete when it returns. The send itself is made in the calling thread, and a failure is thrown there, as for a synchronous send. Only the notification is asynchronous.
* `onCompletion` is called on a virtual thread, never on the thread that called `send`, and the callbacks of one session are called one at a time, in the order of the sends.
* `onException` is never called: nothing can fail after the send has returned.
* A null completion listener throws `IllegalArgumentException`.
* `Session.close()`, `commit()`, `rollback()` and `MessageProducer.close()` wait until the completion callbacks of the sends already made have returned.

From a completion callback, these calls throw `IllegalStateException`: `commit`, `rollback` and `close` on its own session, `close` on a producer of that session, and `close` on its own connection. `Connection.stop()` is not refused from a completion callback: the specification only names message listeners there.

With the simplified API, a `JMSProducer` sends asynchronously once `setAsync(completionListener)` has been called on it.

== Temporary destinations

A temporary queue or topic belongs to the connection that created it. Its typical use is the reply destination of a request:

[source,java]
----
Queue requests = session.createQueue("requests");
TemporaryQueue replies = session.createTemporaryQueue();

TextMessage request = session.createTextMessage("ping");
request.setJMSReplyTo(replies);
session.createProducer(requests).send(request);

// the service side
Message received = session.createConsumer(requests).receive(5_000);
session.createProducer(received.getJMSReplyTo()).send(session.createTextMessage("pong"));

((TextMessage) session.createConsumer(replies).receive(5_000)).getText();   // pong
----

* Any connection of the same broker may send to a temporary destination. Only the connection that created it may consume from it: another one gets a `JMSException` when it creates the consumer.
* `delete()` throws `JMSException` while the destination has a consumer.
* A temporary destination is deleted when its connection is closed.
* Using a deleted temporary destination throws `InvalidDestinationException`.

== Queue browsers

A browser looks at the messages of a queue without consuming them.

[source,java]
----
try (QueueBrowser browser = session.createBrowser(queue)) {
    Enumeration<?> messages = browser.getEnumeration();
    while (messages.hasMoreElements()) {
        TextMessage message = (TextMessage) messages.nextElement();
    }
}
----

* `getEnumeration()` returns a snapshot of the queue at the time of the call. A later call returns a new snapshot.
* The snapshot holds read-only copies, in delivery order. It leaves out expired messages, messages whose delivery time has not come, and messages that a consumer has taken and not yet settled.
* `createBrowser(queue, selector)` shows the messages the selector matches.

== The simplified API

`JMSContext`, `JMSProducer` and `JMSConsumer` offer everything described above with fewer objects. In Tassis they are a thin layer over the classic objects, so the behaviour is the same.

[source,java]
----
try (JMSContext context = factory.createContext()) {
    Queue queue = context.createQueue("orders");

    context.createProducer()
            .setPriority(8)
            .setProperty("color", "blue")
            .send(queue, "hello");

    String body = context.createConsumer(queue, "color = 'blue'").receiveBody(String.class, 5_000);
}
----

=== Session mode

`factory.createContext()` creates an automatically acknowledged context. `createContext(int sessionMode)` takes one of the four `JMSContext` modes, and an unknown mode throws `JMSRuntimeException`. `JMSContext.acknowledge()` acknowledges the consumed messages of a client-acknowledged context and does nothing in the other modes. `commit()`, `rollback()` and `recover()` behave as on a session.

=== Contexts that share a connection

`context.createContext(sessionMode)` returns a new context on the **same connection**, with a session of its own. The connection is closed when the last of the contexts that share it is closed.

[source,java]
----
JMSContext second = context.createContext(JMSContext.AUTO_ACKNOWLEDGE);
TemporaryQueue temporary = context.createTemporaryQueue();

context.close();
// the connection, and its temporary queue, are still there
second.createProducer().send(temporary, "still open");
second.close();
// now the connection is closed
----

A closed context cannot create another one: `createContext` then throws `IllegalStateRuntimeException`.

=== Autostart

A context starts its connection each time it creates a consumer. `setAutoStart(false)` turns this off for that context, and the application then calls `start()` itself:

[source,java]
----
try (JMSContext manual = factory.createContext()) {
    manual.setAutoStart(false);
    JMSConsumer consumer = manual.createConsumer(queue);
    // nothing is delivered yet
    manual.start();
}
----

=== `JMSProducer`

A `JMSProducer` carries the send options (delivery mode, priority, time to live, delivery delay), the headers `JMSCorrelationID`, `JMSType` and `JMSReplyTo`, and message properties. It applies them to each message it sends. A property or a header set on the producer overrides the one the message already carries.

`send` has one form per kind of body: `String`, `Map<String, Object>`, `byte[]`, `Serializable`, and `Message`.

=== `receiveBody`

`receiveBody(Class)`, `receiveBody(Class, timeout)` and `receiveBodyNoWait(Class)` return the body of the next message, or `null` if none arrives in time. They throw `MessageFormatRuntimeException` when the body cannot be returned as that type, when the message has no body, or when it is a plain `Message` or a `StreamMessage`.

What happens to the message after such a failure depends on the session mode:

* in an automatically acknowledged context the message stays exactly where it was: the next receive gets it, and it is not marked as redelivered;
* in a client-acknowledged or transacted context the message counts as delivered, and the application gets it back through `recover()` or `rollback()`.

=== Exceptions and callbacks

Each checked exception of the classic API is reported as its unchecked counterpart, with the checked one as its cause: `IllegalStateRuntimeException`, `InvalidDestinationRuntimeException`, `InvalidSelectorRuntimeException`, `MessageFormatRuntimeException` and so on, or `JMSRuntimeException` when there is no specific counterpart.

A message listener may not close or stop the context it runs on: `close()` and `stop()` throw `IllegalStateRuntimeException`, and the context stays open. A context that is being closed from another thread stays usable by its callbacks in progress, but creates nothing new.

[#authentication]
== Authentication

A broker checks who connects once users are declared on it. `TassisBroker` is the administration of a broker, found by the name a connection factory uses:

[source,java]
----
TassisBroker.named("orders").addUser("billing", password);

ConnectionFactory factory = new TassisConnectionFactory("orders");
try (Connection connection = factory.createConnection("billing", password)) {
    // ...
}
----

A broker is in one of two states.

[cols="1,3",options="header"]
|===
| State | Who connects

| Open: no user has ever been declared
| Anyone. Any user name and password are accepted, and so are the connections created without any. This is the state of a broker nobody administers, which keeps tests and embedded uses free of configuration.

| Secured: from the first `addUser`
| A declared user with its password. A connection created without credentials, with `createConnection()` or `createContext()`, is refused, unless the broker allows anonymous connections: `TassisBroker.named("orders").allowAnonymous(true)`.
|===

A refused connection fails with `JMSSecurityException`, or with `JMSSecurityRuntimeException` from the `createContext` methods. The message does not say whether the user name or the password was wrong.

What to know:

* **A secured broker stays secured.** `removeUser` on its last user does not reopen it to anyone: nobody connects until a user is declared again, anonymous connections aside.
* **A connection already open outlives its user.** Removing a user, or changing its password with a second `addUser`, closes nothing.
* **Users are in memory**, like everything a broker holds: declare them each time the application starts, before the first connection.
* **Every user has the same rights.** Authentication says who may connect; there is no permission by destination.
* **Declare the users before the code that connects runs.** Whoever can call `TassisBroker` in the JVM administers the broker: the registry protects a broker from its clients, which matters once they are remote (milestone M11.3), not from the application that hosts it.

With CDI, `@JMSPasswordCredential` gives the credentials of an injected context. An injection point without it connects without credentials, which a secured broker refuses unless it allows anonymous connections.

[#network]
== Opening a broker to the network

A broker lives in a JVM. `TassisServer`, in the module `tassis-server`, opens it to other processes: it listens on a port and speaks AMQP 1.0, a standard protocol. A Tassis client reaches it by its URL, and so does any other AMQP 1.0 client, which needs nothing of Tassis.

[source,java]
----
try (TassisServer server = TassisServer.forBroker("orders").port(5672).start()) {
    // clients connect to amqp://this-host:5672 until the server is closed
}
----

The broker is the one `new TassisConnectionFactory("orders")` reaches in the same JVM: an application that starts a server keeps using its broker directly, and the clients of the network share its queues.

=== A Tassis client in another process

The application on the other side keeps its code and changes the URL of its connection factory:

[source,java]
----
ConnectionFactory factory = TassisConnectionFactory.fromUrl("tassis:amqp://broker-host:5672");
try (JMSContext context = factory.createContext()) {
    context.createProducer().send(context.createQueue("orders"), "hello");
}
----

It needs one more artifact, `io.vidocq.tassis:tassis-amqp`, which holds the transport. `tassis-core` finds it as a service: on the module path, a module that only provides a service is not resolved by itself, so the application names it, with `requires io.vidocq.tassis.amqp;` in its `module-info.java` or `--add-modules io.vidocq.tassis.amqp` on the command line. An application that also `requires io.vidocq.tassis.server` has it already.

The same address can be given as a setting, `tassis.server=amqp://broker-host:5672`; the port is 5672 when left out. With `amqps` instead of `amqp` the connection is encrypted: see <<tls>>. The user name and the password of `createConnection(userName, password)` are those the broker checks.

What differs from the broker of the JVM:

* **A connection can be lost.** When the broker goes away, or says nothing for two minutes, the `ExceptionListener` of the connection is called, once, with a `JMSException`; every call on the connection then fails, and a `receive` in progress ends with a `JMSException`. Tassis does not reconnect: the application creates another connection. What the lost connection had not acknowledged is delivered again, by the broker, to whoever consumes next.
* **`setClientID` reconnects.** AMQP says who a connection is when it opens. A client identifier set in the settings of the factory is there from the start; one set with `setClientID` closes the connection made without it and opens another. Prefer the factory, as the specification does.
* **A consumer asks for one message at a time.** A message stays with the broker until an application asks for it, so that another consumer can take it: nothing is fetched ahead. Each message costs a round trip.
* **A consumer closed with unacknowledged messages keeps its place** until its session acknowledges them, commits or gives them back: the broker would otherwise deliver them again at once. A durable subscription is therefore still in use, for another connection, until then.
* **A message larger than 16 MiB ends the connection**: it is the limit of the server.

[#tls]
=== Encrypting the connection

A server encrypts when it is given a TLS context, which holds its key and its certificate. The application builds it, with the classes of the JDK, from a key store of its own; Tassis reads no file.

[source,java]
----
KeyStore keys = KeyStore.getInstance("PKCS12");
try (InputStream in = Files.newInputStream(Path.of("broker.p12"))) {
    keys.load(in, password);
}
KeyManagerFactory keyManagers = KeyManagerFactory.getInstance(KeyManagerFactory.getDefaultAlgorithm());
keyManagers.init(keys, password);
SSLContext context = SSLContext.getInstance("TLS");
context.init(keyManagers.getKeyManagers(), null, null);

TassisServer server = TassisServer.forBroker("orders").host("0.0.0.0").tls(context).start();
----

Such a server listens on port 5671, the port of AMQP over TLS, unless told otherwise. It is encrypted from the first octet: a client that speaks in clear to it is turned away, and a server that must serve both starts two listeners, one with a context and one without.

A client says `amqps` instead of `amqp`:

[source,java]
----
ConnectionFactory factory = TassisConnectionFactory.fromUrl("tassis:amqps://broker-host");
----

* **The certificate must be trusted.** By default a factory trusts what the JVM trusts: the certificate authorities of the JDK, or the trust store named by the system property `javax.net.ssl.trustStore`. For anything else, such as a certificate the organisation issued itself, the application gives the factory a context: `factory.withSslContext(context)`.
* **The certificate must bear the name of the host.** The name in the URL is checked against the certificate, as a browser does for HTTPS. There is no setting to turn that off: a certificate is issued to the name clients use.
* **A broker that is not trusted is refused** with a `JMSException` before anything is sent, the password included.
* **The client proves who it is with its user name and password**, now encrypted. The server asks clients for no certificate.
* **The versions of TLS** are those the JDK enables: 1.3 and 1.2 today.

Apache Qpid JMS connects the same way, with `amqps://broker-host:5671` and its own settings for the trust store.

[#third-party]
=== A broker that is not Tassis

The URL `tassis:amqp://host` may name a broker that is not Tassis, as long as it speaks AMQP 1.0 the way Jakarta Messaging clients expect: no standard says how, and Tassis follows the conventions of Apache Qpid JMS, which brokers read. It is tried against one, **Apache ActiveMQ Artemis**, on queues and topics, the kinds of subscription, selectors, transactions, temporary destinations, browsers, delivery delay, authentication and TLS.

What differs there:

* **The broker's rules are the broker's.** What a destination is, how long a message waits, what happens to one that is never acknowledged: Tassis only carries the requests.
* **Giving a message back is not instantaneous.** After `recover`, `rollback` or the closing of a consumer, a Tassis server has the messages back before the call returns; with another broker they are back a moment later, which only another connection could notice.
* **A connection must offer to send without a link per destination** (the capability `ANONYMOUS-RELAY`): a broker that does not is refused when the connection is created.

Another broker than Artemis is untried.

=== Any other AMQP 1.0 client

With Apache Qpid JMS, a Jakarta Messaging client, an application on another machine writes ordinary Jakarta Messaging code, with nothing of Tassis:

[source,java]
----
ConnectionFactory factory = new org.apache.qpid.jms.JmsConnectionFactory("amqp://broker-host:5672");
try (JMSContext context = factory.createContext()) {
    context.createProducer().send(context.createQueue("orders"), "hello");
}
----

[cols="1,3",options="header"]
|===
| Setting | Meaning

| `port(int)`
| The port to listen on. 5672, the port of AMQP, by default; 0 for any free port, which `server.port()` then tells.

| `host(String)`
| The address to listen on. **The loopback address by default**, which only the machine itself reaches. `"0.0.0.0"` listens on every interface.
|===

What to know:

* **Nothing is encrypted unless asked.** In clear, messages and passwords can be read on the way. That is why the server listens on the loopback address unless told otherwise: before opening it to a network, give it a TLS context (see <<tls>>).
* **The users are those of the broker.** A secured broker (see <<authentication>>) asks a client of the network for the name and the password of a declared user, and offers anonymous access only if it allows it. A refused client gets a `JMSSecurityException` from its own provider.
* **A client of the network has the whole of Jakarta Messaging.** Queues and topics, the four kinds of subscription and `unsubscribe`, message selectors, temporary destinations, local transactions, queue browsers, delivery delay: what the application of the JVM has, a client such as Qpid JMS has too. What AMQP 1.0 does not carry is distributed transactions: there is no XA over the network.
* **A client that vanishes loses nothing.** What it had received and not acknowledged goes back to its queue and is delivered again, marked as a redelivery. A transaction it had not committed is rolled back, its temporary destinations are deleted and its non-durable subscriptions end; its durable subscriptions stay.
* **A client identifier is the container identifier of AMQP.** A client that sets one (`Connection.setClientID`, or `jms.clientID` with Qpid JMS) gets its durable and shared subscriptions scoped by it, as in the JVM; one that sets none shares them with every other such client.
* **A client that prefetches may see a message more than once.** A client such as Qpid JMS asks for many messages ahead of the application. A message it gives back while it closes can be sent to it again before it is gone, so `JMSXDeliveryCount` may grow by more than one.
* **Closing the server ends the connections, not the broker.** The messages stay, for the clients of the JVM and for a server started later.

== Injecting `JMSContext` with CDI

An application that runs on Vauban can have its contexts injected instead of creating them (§12.4 of the specification). It adds the artifact `io.vidocq.tassis:tassis-cdi-vauban` and one line to its module descriptor:

[source,java]
----
module com.acme.orders {
    requires io.vidocq.tassis.cdi.vauban;   // brings io.vidocq.tassis.core
    requires jakarta.cdi;
    requires jakarta.inject;
}
----

[source,java]
----
@Dependent
public class OrderDesk {

    @Inject
    JMSContext orders;

    @Inject
    @JMSConnectionFactory("audit")
    @JMSSessionMode(JMSContext.CLIENT_ACKNOWLEDGE)
    JMSContext audit;

    public void place(String order) {
        orders.createProducer().send(orders.createQueue("orders"), order);
        audit.createProducer().send(audit.createQueue("trail"), "placed " + order);
    }
}
----

The bean neither creates nor closes anything. The container must be given the two beans of the integration, which `TassisCdi.BEANS` lists:

[source,java]
----
var builder = VaubanContainer.builder();
TassisCdi.BEANS.forEach(builder::addBeanClass);
try (VaubanContainer container = builder.addBeanClass(OrderDesk.class).build()) {
    ...
}
----

That is the one discovery mode Tassis is tested with. The artifact carries no Vauban bean index, so the scanning modes of Vauban are not known to find these two beans.

=== The life of an injected context

An injected context belongs to the **request** in progress:

* it is created the first time the request uses it, not at injection;
* within a request, the injection points that carry the same annotations share one context, whatever the bean they are in. A message sent through one is received through the other, and they see the same temporary destinations;
* it is closed when the request ends, with its consumers and its unacknowledged messages, which go back to their queue;
* the next request gets a new context.

Used outside a request, an injected context throws the container's `ContextNotActiveException`. That includes a message listener, which runs on a thread of its own: a listener works with the message it is given, not with an injected context. The transaction scope of the specification comes with JTA in milestone M13.

A request that runs subtasks in parallel shares its contexts with them. Like any `JMSContext`, an injected context is used by one thread at a time.

=== The three annotations

[cols="2,3",options="header"]
|===
| Annotation | Effect

| `@JMSConnectionFactory("name")`
| The connection factory to use. Without it, the default one.

| `@JMSSessionMode(mode)`
| The session mode, `AUTO_ACKNOWLEDGE` without it.

| `@JMSPasswordCredential(userName = ..., password = ...)`
| The credentials the connection is created with, checked by the broker once it is secured: see <<authentication>>.
|===

Two injection points share a context when the three give the same values.

=== Where the connection factories come from

The application may supply its factories as beans. The bean without `@Named` is the default factory, and the bean with `@Named("audit")` is the one `@JMSConnectionFactory("audit")` designates:

[source,java]
----
@Dependent
public class Factories {

    @Produces
    @Dependent
    public ConnectionFactory orders() {
        return new TassisConnectionFactory("orders");
    }

    @Produces
    @Dependent
    @Named("audit")
    public ConnectionFactory audit() {
        return TassisConnectionFactory.fromUrl("tassis:vm:audit");
    }
}
----

Without such a bean, the factory is the one the xref:reference.adoc#configuration[settings] describe, read from the **system properties**: `-Dtassis.broker=orders` for the default factory, `-Dtassis.factory.audit.broker=audit` for the factory `audit`. With no bean and no property, an injected context connects to the broker `default`. Two beans for one name throw `JMSRuntimeException` at the first use.

=== What an injected context refuses

Other beans share it and the container manages it, so the methods that would change it for everybody throw `IllegalStateRuntimeException` (§12.4.5): `setClientID`, `setExceptionListener`, `start`, `stop`, `setAutoStart`, `close`, `commit`, `rollback`, `recover` and `acknowledge`.

Two consequences:

* a `SESSION_TRANSACTED` injected context cannot commit what it sends, so that mode is of no use before milestone M13;
* the messages a `CLIENT_ACKNOWLEDGE` injected context consumes cannot be acknowledged, and are redelivered once the request ends. Consume with the default mode.
